### 模型

`sherpa-onnx-sense-voice-zh-en-ja-ko-yue-int8-2024-07-17`（239 MB int8）

選它的理由：zh/en/ja/ko/yue 多語言、支援 ITN（數字正規化）、
反應快，且**與商業競品用的是同一個模型家族**（`hardware.md` §8.6）。

### 已驗證的管線（`--smoke`）

模型內附 5 個測試音檔，全部正確解碼：

| 語言 | 音長 | 解碼 | RTF |
|---|---|---|---|
| en | 7.15s | 133 ms | 0.02 |
| ja | 7.20s | 126 ms | 0.02 |
| ko | 4.61s | 85 ms | 0.02 |
| yue | 5.15s | 92 ms | 0.02 |
| zh | 5.59s | 99 ms | 0.02 |

模型載入 814 ms。**RTF 0.02 → 5 秒語音約 0.1 秒解碼，遠低於 1.5 秒門檻。**

### 🔴 重大發現：SenseVoice 輸出**簡體中文**

實測 `zh.wav` → `开饭时间早上9点至下午5点。`（簡體）。

對台灣使用者而言這是**必須處理的問題**：
直接把簡體輸出跟繁體參考比對，CER 會爆高，但那是**字形差異不是辨識錯誤**。
→ 產品在 ASR 之後需要一道**簡→繁轉換**（OpenCC `s2t`），
   `asr_bench.py` 已把「原樣／統一繁／統一簡」三種基準都算出來，
   避免把字形問題誤判成辨識問題。

### 「準確率 ≥ 95%」的定義（計畫原本沒寫）

本工具同時回報三種定義，避免後續各說各話：

| 指標 | 定義 |
|---|---|
| 字元錯誤率 CER | 編輯距離 / 參考字數（**主指標**，業界標準） |
| 字元正確率 | `1 - CER` → 對應「≥ 95%」的說法 |
| 完全相符句比例 | 整句一字不差的句子比例（最嚴格） |

### ✅ 端到端實測成功（2026-09）

`python tools/p1/transcribe.py --traditional` → 按 Enter 錄 → 按 Enter 停：

| 說話位準 | 有聲比例 | 音長 | 解碼 | 結果 |
|---|---|---|---|---|
| −32.3 dBFS | 45% | 2.82s | 65 ms | `测试一二三。` → **`測試一二三。`** ✅ |
| −40.9 dBFS | 67% | 2.28s | 55 ms | `他是123。`（內容待確認） |

**完整鏈路（麥克風 → ASR → 簡→繁 → 文字）已可用。**
RTF 0.023，2.8 秒語音解碼 65 ms —— 距離 1.5 秒門檻有 20 倍以上餘裕。

**觀察到的位準↔品質關係**（樣本少，僅供參考）：
−32 dBFS 完全正確、−41 dBFS 開始出現偏差。
→ 收音位準值得在 P2/P5 補一個軟體增益或提示，但**不是阻擋性問題**。

### 踩到的坑：麥克風路徑餵錯型別

```
TypeError: accept_waveform(): incompatible function arguments
Invoked with: ..., 16000, b'\xf0\xff\xef\xff...'
```

錄音路徑給的是 PCM **bytes**，檔案路徑給的是 float list —— 只有檔案路徑做了轉換。
**所有既有測試都走檔案路徑，完全蓋不到。**
已改為兩條路徑共用 `pcm_to_samples()`，並補上
[`test_speech_engine.py`](../../tools/p1/test_speech_engine.py)
刻意同時測兩條路徑並斷言結果一致。

### ✅✅ 完整迴路成功：按住錄音鍵 → 說話 → 放開 → 文字出現

`python tools/p1/ptt.py --debug`，實體裝置錄音鍵：

```
· 接受 Ctrl DOWN flags=0x2 make=29 dev=BT-HID/Col01
🔴 錄音中…（BT-HID/Col01）
⏹  停止（3.5s，音訊 3.48s）
📝 測試一二三四五七。   （辨識 71 ms）
✅ 已注入（paste，279 ms）
⏱  端到端（辨識+注入）350 ms
```

**端到端 350 ms** —— 距 1.5 秒門檻有四倍餘裕。

同時驗證到的正確行為：

| 情境 | 行為 |
|---|---|
| 按住時的自動重複 DOWN | 正確忽略（`pressed=True` 不再觸發） |
| 實體鍵盤的左 Ctrl（`flags=0x0/0x1`，無 E0） | 正確忽略 |
| Apple 鍵盤的 Ctrl（`make=29` 但無 E0、裝置不符） | 正確忽略 |
| 我們自己注入的 Ctrl+V（`make=0`、無裝置） | 正確忽略 → **無回饋迴圈** |

### ⚠️ 暖機的必要性（實測踩到）

第一次按下時 `音訊 0.00s`（完全沒資料）。追查後發現：
**這支藍牙麥克風冷啟動要 1.19 秒才會有音訊**，而使用者按放得比它快。
連線建立後不會因閒置而斷（閒置 20 秒後再開只要 0.04 秒）。
→ `ptt.py` 加入 `warmup_audio()`，啟動時輪詢到真的收到音訊才接受按鍵。
詳見 [`../hardware.md`](../hardware.md) §2.1。

### 停止方式改為手動（依原廠流程）


原廠是「按鍵開始 → 停止」。自動停止的 VAD 門檻實測表現不佳
（8 段錄音有聲比例僅 9–33%，某句 19 字只錄到 0.24 秒），
已把**手動按 Enter 停止設為預設**，`--stop auto` 保留。
