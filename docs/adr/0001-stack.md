## 背景

需要一個跨平台（Windows / macOS / Linux）的常駐 Tray 桌面程式，具備：

1. 從**指定**藍牙音訊裝置錄音
2. 全域按鍵按下／放開偵測（**任意鍵碼**，見 AGENTS.md §8）
3. 本地 ASR 推論（sherpa-onnx）
4. 對前景視窗注入文字（剪貼簿貼上 + 逐字輸入退路）
5. 單一、可安裝、不被防毒誤報的安裝包

三個候選：**Rust + Tauri 2**、**Python**、**Go**。

**已預先記錄的已知事實（不算分，但影響判斷）：**

- 開發機**尚未安裝 Rust 與 Go**；Python 3.14 + onnxruntime 1.28 已就緒。
- ~~目標裝置的按鈕鍵碼尚未量測~~ → **P0 已量測完畢，見下方「熱鍵可行性」**。

### 熱鍵可行性（P0 實測，直接改變評分基準）

`hardware.md` §3.3、§3.4 確認：

1. 裝置 6 顆按鈕送的是 **Enter / Backspace / 上下左右**，都是**標準鍵盤事件**。
2. 這些鍵**會漏進前景視窗**（Enter 送出、Backspace 刪字、方向鍵移動游標）。
3. 因此熱鍵層**必須抑制按鍵**；但可抑制的機制（低階 hook）**無法辨識裝置**，
   而可辨識裝置的機制（Raw Input）**無法抑制**。

→ **「全域熱鍵」的評分基準必須改為：**

| 舊基準 | 新基準（P0 後） |
|---|---|
| 有沒有現成的全域熱鍵函式庫？ | 能不能實作「**可抑制 + 可辨識裝置**」的雙通道 hook？ |

這對三棧都不利，而且**沒有現成 crate / 套件可以直接用**：

| 棧 | 現成方案 | 是否符合新基準 |
|---|---|---|
| Rust | `global-hotkey` | ❌ 不抑制、不辨識裝置 → 需自行用 `windows-rs` 寫 hook |
| Python | `pynput(suppress=True)` | ⚠️ 可抑制但無法辨識裝置 → 仍需自行接 Raw Input 關聯 |
| Go | `robotgo` / `go-hook` | ⚠️ 同上，且 cgo 包裝維護度參差 |

**這一項可能成為決勝點**：三棧都得自己寫，差別在於「寫得出來的程度」與
「能不能穩定拿到裝置身分」。

### 另一個 P0 事實：原廠工具必須排除

`hardware.md` §8：裝置綁定了原廠工具「閃電說」（`shandianshuo`），
會自動啟動、注入按鍵、搶佔按鈕與麥克風。
**三個棧都必須實作「偵測並要求使用者關閉原廠工具」的引導流程** —— 此項不影響選棧。

### 外部實證：同利基的商業產品用 Tauri 打造

`hardware.md` §8.6 實測：原廠工具「閃電說」v0.7.8 是一個 **Tauri 應用**
（exe 內含 `tauri` / `tao` / `wry` / `WebView2`，資料在
`%LOCALAPPDATA%\cn.shandianshuo.desktop\EBWebView`）。

它在**完全相同的利基**上出貨，且已實作：全域熱鍵（含 `block_keys` 阻擋鍵）、
文字注入、本地 + 雲端 ASR、靜音錄音。

→ **這是「Rust + Tauri 在本領域可行」的實證**，權重高於任何合成 benchmark。
→ 但它也提高了標準：Tauri 若勝出，理由不能只是「能動」，而是
   「能做出競品做不到的事」（全本地、可稽核、體積更小）。

## 決策門檻（事前承諾，避免事後找理由）

| 條件 | 行動 |
|---|---|
| Rust 總分 ≥ 4.0 且無致命缺陷 | **直接選 Rust + Tauri 2** |
| Rust 出現致命缺陷（某平台熱鍵／注入無解） | 跑完 Go，與 Python 二選一 |
| 三棧皆不達標 | **縮小平台範圍**（例：先只做 Windows），而不是硬撐三平台 |

「致命缺陷」定義：**會導致某平台無法達成驗收標準第 1 條**（按住 → 說 → 放開 → 出字）的問題。
